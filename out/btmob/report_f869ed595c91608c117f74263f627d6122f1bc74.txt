[Update - 26th October 6:51PM AEDT] Group-IB’s confidence level for attribution to Lazarus has been downgraded from HIGH to MODERATE - at the time of writing, no secondary sources have been identified corroborating the activity or infrastructure and attribution is mainly based on primary language and target prioritisation. PHP2Shell Vulnerability Background PHP2Shell is the collective name for two critical, unauthenticated remote code execution vulnerabilities in the PHP runtime itself: CVE-2026-109618 and CVE-2026-109619. Both carry a CVSS v4.0 score of 9.2. Technical details leaked publicly on 20 October 2026, ahead of coordinated disclosure, and the PHP project released fixes on 21 October 2026. The two bugs share a single root cause: PHP's longjmp()-based "bailout" mechanism aborts a request mid-operation and can leave internal state half-built or pointing at freed memory. In worker-based deployments, a subsequent request handled by the same worker inherits that stale state, which is what the attacker abuses. Both issues have been reproduced in research, with the original disclosure chaining the two memory-safety flaws using frontier AI models. For more details on PHP2shell, read the main report on the vulnerabilities here. Campaign Overview and Progression On 22 October 2026 (approximately 11:00 JST / 10:00 SGT), closed-source collection surfaced a Korean-speaking threat actor coordinating, through a closed I2P (Invisible Internet Project) channel, global reconnaissance and attack planning against all web-accessible assets carrying the two PHP2Shell vulnerabilities. Two operator handles - one assessed as tasking and lead, the other as collection and exploit triage - have been active since March 2026. Group-IB assesses this activity with MODERATE confidence to be a North Korean state-nexus operation and with MODERATE confidence to be affiliated with the Lazarus Group ecosystem. No launch date has been stated. The activity has been tracked across three observation points. On 22 October the operators set tasking and sector/geography priorities and shared fifteen pieces of campaign infrastructure in-channel for staging, target-list hosting and launch. By 23 October, seventeen suspected source IP addresses were identified within an 8-hour window performing PHP web-shell tooling and upload-progress session poisoning; on their own these did not link to the channel at that time and were published as additional hunting and blocking indicators. Unlike the 23 October position, which could not tie the seventeen newly observed source IPs to the channel, the twenty-one scan-node addresses are the same addresses the operators named as the nodes running their PHP weakness checks, and they were observed in the 8 hours preceding the update performing PHP web-shell tooling and upload-progress session poisoning attempts. This directly tied the scan nodes to the channel. The exchange marks the campaign's progression from reconnaissance and infrastructure staging into active, low-and-slow scanning of a filtered target set; at the time of the exchange roughly one third of the 216 hosts had already been touched. The next adversary milestone is the first-pass result across all 216 hosts and a refined shortlist of highest-confidence hosts, from which the operators will choose which public exploit approaches are worth adapting. Operator Tradecraft and OPSEC The operator is assessed as disciplined and access-focused, harvesting public proof-of-concept code, ranking it with AI, lab-validating before use, and avoiding noisy scanning. Coordination takes place in a closed I2P channel chosen for anonymity, with staging and collection points kept separate from the active scan nodes. The observed tradecraft: AI-assisted PoC triage — local AI is used to rank public proof-of-concept repositories and accelerate reconnaissance, compressing the historical gap from disclosure to reliable weaponisation; the operators state AI is only for "speed on sorting and validation of open material". Public-code-only policy — the operators direct use of public technical descriptions and public exploit code, with an explicit instruction not to invent new primitives, focusing on the out-of-memory path and the stale-state path exploitable in common Apache and FPM setups without local access. Manual lab validation — public repositories are manually verified in a controlled lab before use. Scan avoidance — passive collection of public banners and version strings, staying off assets that look already heavily monitored, building a shortlist of likely-vulnerable hosts first, and avoiding broad noisy scanning. Node rotation and burn discipline — slow rotation through the node list, with addresses showing filtering or rate-limiting dropped immediately and never reused. Patch-aware filtering — hosts that appear to have applied the 21 October patches are flagged and dropped from the target set. A consequence of the public-code-only policy is a faster weaponisation cycle: AI-assisted triage of public PoCs shortens the disclosure-to-exploit gap, so patch and mitigation timelines should be measured in hours, not days. The flip side for the operators is exploit-supply risk. Public proof-of-concept repositories are of unverified or disputed quality, some require GDB or local access, and several circulating "PoCs" are fake and distribute malware, so public tooling must be treated as untrusted and audited before use. Expected Attack Path One unauthenticated multipart POST against an unpatched worker can reach code execution before any application code runs; there is no vulnerable route to discover and little application-layer trace, which also means forensic visibility is poor. The anticipated progression, mapped from the intercepted tasking, open-source exploitation telemetry and historical web tradecraft, moves through the following phases: Reconnaissance — passive banner and version fingerprinting of PHP; country- and sector-segmented target-list building; probing of multipart endpoints and session upload-progress; AI-assisted ranking of public PoCs. Resource development — acquisition and adaptation of public PHP2Shell exploit code; staging on campaign infrastructure; lab validation before use. Initial access — exploitation of CVE-2026-109618 / CVE-2026-109619 via crafted multipart/form-data for unauthenticated RCE, with highest success against Apache mod_php in default prefork. Execution and persistence — command execution as the web-worker user; PHP/ASP web-shell deployment in web roots; cron and SSH-key implants; abandoned-config persistence. Credential access and collection — harvesting of wp-config.php, .env, database credentials and API keys; roughly 67 KB of memory disclosure via PHPSESSID; configuration and file reads via the OPcache primitive. Command-and-control and impact — loader fetch-and-run from a staging host (Mirai convention); outbound C2 from web workers; cryptomining, ransomware, lateral movement and data exfiltration. Request-side signals are useful but noisy, and application logs will usually show nothing because no application code ran. All hunting should start from 17 October 2026, and because the scanning is deliberately low-volume, reviews must cover extended time windows rather than relying on rate-based alerts. The highest-value behavioural and host indicators are: Unusual multipart/form-data POSTs to non-upload endpoints (e.g. '/', '/index.php'); PHP_SESSION_UPLOAD_PROGRESS fields on endpoints that never take uploads. Very high multipart part/field counts, or field names nested dozens of levels deep; bodies of a few hundred KB. PHP worker crashes / OOM fatals in bursts ('Allowed memory size exhausted', 'zend_mm_heap corrupted', SIGSEGV) correlated with preceding multipart POSTs; HTTP 500 on PHP endpoints. Web-server/PHP processes (php-fpm, php-cgi, httpd, apache2, lsphp, frankenphp) spawning shells, interpreters or download tools (sh, bash, curl, wget, nc, busybox), or executing from /tmp, /var/tmp, /dev/shm. New or modified .php / .phtml / .phar files in web roots; .user.ini / .htaccess changes adding auto_prepend_file; new cron jobs, local users or SSH authorized_keys. Abnormally large PHPSESSID values in Set-Cookie (memory disclosure); outbound connections from web workers to uncommon destinations or I2P egress. A process-creation detection should alert where a PHP or web-server parent (php-fpm, php-cgi, httpd, apache2, lsphp, frankenphp) spawns a shell, interpreter or download tool, or launches an image from a temporary directory. A read-only host-triage pass confirms the serving binary and configuration and searches for recently changed PHP files and known markers: php -v # confirm the SERVING binary, not only CLI php -i | grep -E 'session.upload_progress|memory_limit|post_max_size|max_input_nesting_level|fatal_error_backtraces|opcache.enable' find /var/www -type f -name '*.php' -newermt '2026-10-17' -ls find /tmp /var/tmp /dev/shm -type f -perm -u+x -newermt '2026-10-17' -ls grep -rIl -e '92[.]118[.]112[.]100' -e 'JACKALPOC' /var/log 2>/dev/null PHP2Shell exploitation happens in worker memory before application code runs and writes no file by itself, so file-based rules cannot detect the exploit directly; a YARA set instead covers what the attack leaves behind — captured requests and logs, PHP session files, second-stage payloads and web shells dropped after successful RCE, and staged exploit tooling. The nine rules provided are: PHP2Shell_SecondStage_ELF_SHA256 (High) — the second-stage ELF x86-64 binary by SHA-256 and exact size; scan /tmp, /var/tmp, /dev/shm and web roots, noting the loader may delete the file after launch. PHP2Shell_Captured_Request_Body_SHA256 (Medium) — saved scanner and OOM-tool request bodies by exact hash; fragile, as any change to boundary or field values defeats it. PHP2Shell_Infrastructure_IPs_In_Content (Medium) — anonymisation-network, scanner and staging IPs in logs and text content; a hit means investigate, not confirmed compromise. PHP2Shell_Request_Shape_In_Capture (Medium) — scanner user-agents, boundaries, the JACKALPOC marker, or the exploit request shape; run only on per-request captures, not multi-request logs. PHP2Shell_Log_Crash_Signatures (Low) — PHP and PHP-FPM log lines from trigger attempts; side effects, not proof, so correlate with multipart POSTs from the same source. PHP2Shell_Session_File_Anomaly (Medium) — session files containing PHP code, or a residual upload-progress entry with an empty-filename spray. PHP_Webshell_Input_To_Exec_Heuristic (Medium) — generic web shells passing request input to execution or evaluation; not PHP2Shell-specific, so validate against application code. PHP_Suspicious_Command_Execution_Hunting (Low) — broad hunting for PHP files combining command execution with shell paths, request input or decoding; hunting only, not alerting. PHP2Shell_Public_PoC_Script (Low) — staged exploit scripts referencing PHP2Shell CVEs or tooling strings with the upload-progress field; hits on analyst systems may also indicate a trojanised PoC. User-agent, boundary and marker strings are trivially changed by attackers, so the request-shape, session-file and payload rules should be weighted over string matches. Seven of the nine rules will match the rule file itself and other detection content, so rule repositories and threat-intelligence feeds should be excluded from scans. Recommended Actions and Mitigations Immediate (P1) actions: Inventory every PHP runtime — VMs, containers, Kubernetes, appliances, CI/CD, shared hosting and bundled PHP in vendor software — prioritising internet-facing systems, and confirm the live web-serving process version (Apache/FPM), not only the CLI binary. Patch to PHP 8.5.12+, 8.4.27+, 8.3.36+ or 8.2.35+ (or a verified vendor/distribution backport) and restart ALL PHP workers; a reload that keeps old workers alive leaves the stale state in place. Hosts still bannering older PHP are the ones the operators kept. Isolate or take offline any internet-facing PHP that cannot be patched within hours, with Apache mod_php the highest priority; organisations in the prioritised sectors and geographies should treat this as urgent. Block or closely monitor the three catalogued address sets — the 15 staging addresses, the 17 source IPs and the 21 scan nodes — at perimeter and host level, and block the dropper staging host and loader URL on egress. Short-horizon (P2, 72 hours) actions: Hunt back to 17 October 2026 across extended windows for malformed multipart POSTs, session upload-progress anomalies, PHP worker crashes/OOM, web-server processes spawning shells, new PHP files in web roots, and any prior contact with the listed indicators. If compromise is suspected, preserve volatile evidence before patching (restarting workers destroys CVE-2026-109619 state), capture memory and logs, isolate the host, rebuild from a trusted patched image, and rotate all secrets accessible to the PHP worker. Seven-day (P3) action: notify relevant national CERTs and sector coordination channels and brief leadership, watching for the catalogued infrastructure, I2P egress, a launch statement or the operators' refined shortlist. Temporary controls reduce exposure while patching is scheduled but do not replace it — a fixed release is the only complete mitigation. The two bugs require different interim controls. CVE-2026-109618 interim controls memory_limit = -1 (admin-enforced via php_admin_value) post_max_size = 8M where uploads are not required, 32M where they are constrain multipart body size, part and header counts at the reverse proxy max_input_nesting_level = 32 use cgroup/container memory boundaries (not RLIMIT_AS / RLIMIT_DATA) CVE-2026-109619 interim controls session.upload_progress.enabled = 0 (administrative config, not ini_set) fatal_error_backtraces = 0 (PHP 8.5) remove pre-init diagnostics and attacker-reachable fatal paths pm.max_requests = 1 (where performance allows) For defence in depth: deploy or confirm WAF protections as a supplement; lock origins to CDN/WAF ranges so attackers cannot bypass to the origin IP; and egress-filter web workers, blocking 92[.]118[.]112[.]100 and hxxp://92[.]118[.]112[.]100/nfs.
