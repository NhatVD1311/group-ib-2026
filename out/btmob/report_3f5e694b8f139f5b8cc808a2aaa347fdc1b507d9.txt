SiriusQT, a Windows RAT sold on underground forums since 2026, combines HVNC, credential theft and custom encrypted C2. Analysis of its server, client and licensing. Introduction SiriusQT is advertised as a Windows RAT, but the analyzed sample in this article shows something more complex than a remote administration tool. Under the name, it offers several capabilities in a single implant: remote access, HVNC, browser automation, credential theft, cryptocurrency wallet collection, clipboard monitoring, keylogging, process injection, persistence, anti-analysis checks, and custom encrypted command-and-control traffic. This article walks through SiriusQT's server- and client-side components, highlighting what makes it interesting from a reverse-engineering perspective. The goal is not only to list its features, but to show a complex cluster of affiliates, their campaigns and how these components work together and why SiriusQT should be treated as a serious RAT and stealer platform. Key discoveries SiriusQT is a RAT found for sale on dark web forums since April 2026. Its author is named “Amonus”, but the seller is “GhostKernel”. At least 30 users bought a valid license. Licenses can be of different sizes: one month, three months, lifetime. Licenses can also be customized by the SiriusQT operator depending on customer requests. 14-day licenses, 45-day licenses, and also 99-day licenses were spotted during the analysis. Malicious campaigns were targeting, among others, the United Kingdom, Germany, France, Spain, Italy, and the Netherlands. Embeds Hidden Virtual Network Computing (HVNC) for victims' remote control. Strong stealing and keylogging capabilities are also oriented toward extracting data from cryptocurrency wallets and most-used programs. Multiple Process Injection Techniques. Persistence The SiriusQT RAT can be configured to start using different startup methods, including: a Registry Run key a Scheduled Task a shortcut in the Startup folder a logon script the BootExecute registry value (but requires the malware to have administrator privileges), which runs before normal user logon Windows Default User profile These options are up to the operator to be activated during the stub building phase. They allow the SiriusQT to adapt to different environments and privilege levels. If the registry run key option is enabled, the sample implements user-level persistence through the HKCU\Software\Microsoft\Windows\CurrentVersion\Run registry. If no custom value name is provided, it uses the Windows Update name. This allows the payload to be launched automatically when the user logs in, without requiring any administrative privileges. When the schedule task option is enabled the SiriusQT client side component builds an XML task definition and creates it using schtasks.exe. The generated task is configured with a logon trigger, intended to run when the user logs in. If no custom task name is provided, the malware uses the name Windows Update. When the Startup Folder option is enabled, the RAT initializes COM interface and creates a Shell Link object. It sets the shortcut target to the configured payload path, assigns the description Windows Update, and then saves the shortcut as a .lnk file, using WindowsUpdate.lnk as the default name. The RAT implements persistence through the UserInitMprLogonScript mechanism. When the Logon Script option is enabled, the RAT creates a batch script named logon.cmd, in the directory provided in the configuration stub. The script contains a command that starts the SiriusQT client side component. After creating the script, the malware opens HKCU\Environment and sets the UserInitMprLogonScript value to the path of the generated logon.cmd file. This causes the script, and therefore the RAT, to be executed when the user logs in. This is a user-level persistence technique and does not require administrative privileges. When the Boot Execute option is enabled, the malware attempts to use an administrator-level persistence and more stealth method than normal user-level startup persistence. It first checks whether it is running with administrative privileges. If so, it opens the Session Manager registry key HKLM\SYSTEM\CurrentControlSet\Control\Session Manager and queries the existing BootExecute value. By appending an additional entry to it, the SiriusQT RAT can attempt to execute code during system startup. When the SiriusQT has the Default User persistence option it poisons the Windows default User Profile. This is because Windows uses C:\Users\Default as a template when creating new user profiles. The file C:\Users\Default\NTUSER.DAT contains the registry hive that will be used as the base for the new user’s HKEY_CURRENT_USER hive. The SiriusQT abuses this behavior by loading the Default User registry hive with RegLoadKeyA, modifying it, and then unloading it with RegUnLoadKeyA. While the hive is loaded, the malware writes an autorun-style registry value. If no custom value name is found in the configuration, the value is named Windows Update. The data written by the RAT uses %APPDATA%, this means the RAT attempts to seed persistence both in the current user profile and into future user accounts created on the same machine. Dynamic API resolution Once the SiriusQT client ends setting the persistence mechanism, it starts walking the PEB structure, enumerating module exports, and resolving the API using a custom 32bit FNV-1 hash algorithm. FNV-1 hash algorithm in SiriusQT client side component. In the above evidence, the seed is 0x7158B20F and the target hash is 0x62A6C3F7, which resolves to CreateThread API. Another function was found using the same algorithm but with the seed 0x29f1276c and resolving the 0x706ECA3E hash, corresponding to LoadLibraryA. A python script is provided for fast hash computation: def sirius_api_hash(api_name: str) -> int: h = 0x7158B20F fnv_prime = 0x01000193 for b in api_name.encode("ascii"): h ^= b h = (h * fnv_prime) & 0xFFFFFFFF return h target = "CreateThread" hash_value = sirius_api_hash(target) print(f"{target} -> 0x{hash_value:08X}") The client dynamically resolves LoadLibraryA and GetProcAddress through PEB, using the same FNV-1a like hashing algorithm, loads iphlpapi.dll, and obtains the address of NotifyAddrChange API. This allows the main C2 server to be automatically reconnected after the network stops working or the internal IP address changes. Payload execution SiriusQT also includes multiple ways of doing process injection and in-memory payload execution. It references APIs and techniques such as WriteProcessMemory and VirtualProtectEx. In addition, it resolves dynamically API like NtQueryInformationProcess and NtQueueApcThread. The SiriusQT server-side component let choose between Process Hollowing and different injection techniques like QueueUserAPC / Early-Bird Injection and Remote Thread Injection using NtCreateTreadEx or CreateRemoteThread APIs, designed to run both EXE and DLL x32/x64., available on the client-side component. The payload execution form also allows choosing the running target process on the client: Remote execution option panel in SiriusQT server-side component. HVNC Like many modern RATs, SiriusQT RAT provides an HVNC feature. HVNC, or Hidden VNC, gives the attacker a remote graphical session inside a hidden desktop that the victim does not normally see. The HVNC protocol between the client and the server is discussed in the Command and Control section. Before that HVNC session starts, the SiriusQT server-side component delivers an additional DLL module to the SiriusQT client, named HVNCInjection.x64.dll . It supports the hidden session by installing hooks, redirecting selected file-system paths, and injecting itself into child processes created during the HVNC session. The HVNCInjection.x64.dll module has the following SHA-256 hash: c206fa613257110b0522b60b402ca0b35da2cb126113e47b67543ba3ff93c53c This DLL contains a reflective loading mechanism. This means that the HVNCInjection.x64.dll could be loaded directly from memory instead of being loaded from disk by the Windows loader. The reflective loader locates the DLL image in memory, validates the PE headers, allocates memory for the new image, copies headers and sections, resolves imports, applies relocations, and finally calls the DLL entry point. Inside the reflective loader stage, the loader dynamically resolves Windows APIs. It walks the loaded module list from the PEB and computes a ROR13-based hash over module names. For example, the comparison with the hash value 0x6A4ABC5B identifies kernel32.dll library. ROR13 based hash algorithm in HVNC helper module named HVNCInjection.x64.dll. The HVNCInjection.x64.dll DLL uses MinHook to install userland hooks. MinHook is a small user-mode API hooking library for Windows. It allows the SiriusQT client-side component to intercept API calls, forcing the execution first to the DLL’s custom handler. The handler can inspect and modify the parameters, then call the original API through a trampoline created by MinHook. When the DLL is loaded the following APIs are hooked: NtCreateFile NtOpenFile NtDeleteFile NtSetInformationFile NtQueryAttributesFile NtQueryFullAttributesFile This means the DLL can redirect file creation, file opening, file deletion, rename or move operations, and file attribute queries. The DLL also installs hooks on: NtQueryDirectoryFile NtQueryDirectoryFileEx However, for these two last APIs the handler does not modify the returned directory listing, it simply calls the original function, so the handler acts like a wrapper. The DLL also provides a way to do filesystem path redirection based on two environment variables RDI_SEARCH_PATH and RDI_REPLACE_PATH. When a process tries to access a file path, the hook checks whether that path matches the value configured in RDI_SEARCH_PATH. If it does, the DLL changes the path by using the value configured in RDI_REPLACE_PATH. The process believes it is accessing the original path, but the real Windows API receives the replaced path. For example, if the two environment variables are configured like the following: RDI_SEARCH_PATH = C:\Users\Admin\Desktop RDI_REPLACE_PATH = C:\Users\Admin\AppData\Local\Temp\HiddenDesktop then a request for accessing the “C:\Users\Admin\Desktop\file.txt”, can be redirected to the “C:\Users\Admin\AppData\Local\Temp\HiddenDesktop\file.txt” . This mechanism is transparent to the process that is trying to access the “C:\Users\Admin\Desktop\file.txt”, but the real API call uses the redirected path once the handler modified it. Using HVNC, the SiriusQT operator can interact with applications installed on the client machine, while selected file paths are transparently redirected to a separate location. This can help isolate the HVNC environment from the victim’s real desktop or profile paths, depending if the two path variables are enabled and how they are configured. The SiriusQT client embeds the code for launching a Chromium-based browser instance for the HVNC module: Command line for launching the chromium based browser in the SiriusQT client. It builds a dedicated browser profile path, checks whether the profile directory exists, and prepares it if needed. The browser is then started with a custom “--user-data-dir” and an inline “data:text/html” page displaying “Welcome to HVNC !”. The command line also is intended for disabling sandboxing, GPU acceleration, audio, plugins, 3D APIs, and other rendering features, just like for doing as little noise as possible to run a HVNC environment. When the operator executes the browser app (for instance Edge) in the HVNC session, he can also clone the browser profile resulting in complete client session stealing: HVNC panel in SiriusQT server-side component. Apps started within the HVNC session are children of the SiriusQT client process. For this reason the HVNCInjection.x64.dll also embeds a CreateProcessW hook. This is important for HVNC sessions because applications launched inside the hidden session may create additional processes and if the DLL remained in the first process only, the redirection logic would not apply to child processes. When a new process is created, the CreateProcessW hook forces the CREATE_SUSPENDED flag. This makes the child process start in a suspended state. Command & Control The SiriusQT RAT communication channel is encrypted at the payload level. The protocol uses a simple TCP framing format where each message starts with a 4-byte little-endian payload length. This length field is transmitted in cleartext and is used only to determine how many bytes must be read from the TCP stream. The following payload bytes are encrypted. SiriusQT Client - Server encrypted communication channel format. The same frame structure is used in both directions. Only the payload is encrypted. SiriusQT does not appear to use a standard encryption algorithm such as ChaCha20 or Salsa20 for its network traffic, even though the binary contains the string “expand 32-byte k”. The SiriusQT communication is encrypted using a custom stream-cipher-like routine for payload transport and receiving data. While looking at the SiriusQT client-side component, the function at 0x1400D82C0 receives a cipher context, a buffer, and a buffer size, then modifies the buffer in place. SiriusQT Client - Server encrypting clear-text buffer. The cipher context is made up of: the 32-byte communication key stored in the configuration the current 64-bit packet counter For each payload, the 64-bit counter is read from the context and then incremented: Cipher context for clear-text buffer encryption. The encryption routine combines the counter, the current payload offset, and values from the cipher context to derive temporary 64-bit values. These values are then mixed using two constants associated with the MurmurHash3 fmix64 finalizer algorithm: 0xFF51AFD7ED558CCD 0xC4CEB9FE1A85EC53 The resulting mixed values are used to build a 16-byte keystream block. This keystream block is then XORed with the cleartext buffer. Conclusion SiriusQT illustrates how modern commodity RATs continue to evolve around the operational needs of financially motivated threat actors. Operators are not only looking for basic remote access capabilities, but for tools that are stable, commercially supported, feature-rich, and capable of maintaining access while reducing detection opportunities. At the same time, the analyzed client shows high detection rates, which limits its effectiveness when deployed directly as a standalone binary. This suggests that successful operators would likely pair SiriusQT with an external loader, packer, or fileless execution chain to reduce exposure during initial execution and improve the chances of establishing a working infection. The HVNC implementation is particularly relevant because it could provide operators with an isolated hidden desktop environment. HVNC is not an auxiliary feature, but a core capability intended to support stealthy interactive activity on infected systems. This type of functionality is increasingly valuable in the MaaS RAT ecosystem, where operators look for tools that enable hidden browser-based fraud rather than opportunistic credential theft. Recommendations Stay alert to any request asking you to download, open, or execute files, especially when the request comes from emails, messaging platforms, fake support pages, cracked software websites. Always verify the source before proceeding to reduce the risk of exposing your device, credentials, or organization to malware. Enforce Multi-Factor Authentication (MFA) across all critical services and monitor for suspicious login activity. While session hijacking through stolen cookies or cloned browser profiles can bypass password-based authentication, MFA still increases the difficulty for attackers attempting to gain or maintain unauthorized access. Keep operating systems, browsers, password managers, and security tools regularly updated. Browser security features, such as Chrome’s App-Bound Encryption, are designed to reduce unauthorized access to stored secrets, but their effectiveness depends on timely updates and proper endpoint protection. Maintain visibility into endpoint and network activity. Even commodity RATs can provide operators with remote access, credential theft, file management, proxying, and hidden desktop capabilities. Monitoring unusual outbound connections, suspicious browser activity, and unexpected execution behavior can help identify compromise earlier.
