Malicious ISO File Leads to Quantum infection
['https://thedfirreport.com/2023/04/03/malicious-iso-file-leads-to-domain-wide-ransomware/']

The intrusion began with the execution of the IcedID malware, which was concealed within an ISO image. This ISO file was delivered to the victim as part of a malspam campaign. The use of ISO images to deliver payloads has become increasingly common among threat actors seeking to evade security controls such as Mark-of-the-Web. Upon opening the ISO image, a hidden directory containing the IcedID payload and a batch file was revealed. When the victim clicked on the malicious LNK file within the virtual hard drive, it triggered the execution of the batch file. This batch file copied the IcedID payload to the user's AppData\Local\Temp folder and loaded it using rundll32. Simultaneously, a scheduled task was created to maintain persistence on the compromised host. After the execution of the IcedID payload, the attackers initiated various discovery commands using Windows utilities, including net, nltest, and ipconfig, to gather information about the domain, domain trusts, domain admins, and workstation configurations. Approximately 16 hours after the initial execution, the attackers executed the first Cobalt Strike beacon DLL from the IcedID malware, leading to additional discovery using net and AdFind. During AD enumeration, the operator utilized the PowerShell Get-Help cmdlet to troubleshoot the following commands: powershell.exe Get-Help Export-CSV powershell.exe Get-Help Get-ADComputer Furthermore, two file-sharing websites, specifically dropmefiles[.]com and file[.]io, were employed to access files. Both of these services were accessed on the second day from one Domain Controller on the network, primarily for downloading various tools and scripts. Subsequently, on the third day, a second Domain Controller was observed accessing the dropmefiles[.]com domain. A more comprehensive examination of the WebCacheV01.dat on the domain controllers revealed additional insights into the visited sites, as well as the files that were downloaded from these websites: The threat actors downloaded the lsass.exe beacon from their infrastructure hosted at 199[.]127[.]60[.]117. The threat actors further escalated their activities by installing remote access software, Atera, and Splashtop via an MSI file. They attempted to exploit the CVE-2020-1472 (ZeroLogon) vulnerability but were thwarted by antivirus software. Subsequently, they used a batch script to perform DNS lookups on various hosts across the environment. Lateral movement was initiated when the attackers copied their Cobalt Strike DLL to a server within the network and executed it via a remote service. The installation of remote access software was repeated. Several hours later, another Cobalt Strike beacon was executed, allowing the threat actors to elevate privileges to SYSTEM on the compromised host and dump LSASS memory. They continued their actions using system tools, batch files, and Adget. Multiple beacons were loaded onto the host using DLLs and PowerShell. At this stage, the threat actors obtained clear-text credentials for one of the domain administrator accounts, enabling them to move laterally to other systems. They issued remote commands using WMIC for discovery and attempted to distribute and execute Cobalt Strike beacons. However, these actions failed to launch a beacon on the targeted domain controller. Faced with repeated failures, the threat actors resorted to RDP access on the domain controller. From there, they downloaded Cobalt Strike PowerShell code from the site textbin[.]net and attempted to execute it locally, which also failed. They then attempted to download various beacon executables (e.g., lsass.exe, lsasss.exe) but continued to experience crashes and failures. Approximately one hour into the RDP session, the threat actors executed a PowerShell command to disable Windows Defender Antivirus on the host and reviewed Group Policy Objects for the domain. Subsequently, the Cobalt Strike beacons successfully executed on the domain controller. With Cobalt Strike beacons active on the domain controller, the threat actors continued their discovery actions using tools like Invoke-ShareFinder and various PowerShell and system utilities. Several hours later, the threat actors installed RSAT tools on the beachhead host, although they appeared unfamiliar with the tools and had to consult the help menu before using them to collect information about hosts in the environment. Back on the domain controller, the threat actors utilized ProcDump to dump LSASS memory and collected logon events for all domain administrators in the network using the PowerShell command Get-EventLog. Following a period of inactivity lasting approximately seven hours, the threat actors resumed their activities by launching more Cobalt Strike beacons and executing various Mimikatz implementations on the domain controller, including both binary and PowerShell versions. This activity persisted for several hours and included repeating previous discovery actions and launching additional beacons using remote WMIC commands. During this phase, Windows event logs indicated that the threat actors executed DCSync activities on one of the domain controllers. They also executed a batch file named localdisk.bat using remote WMI commands to collect disk data on hosts throughout the environment. These discovery actions were repeated multiple times using various batch files. On the fourth day of the intrusion, the threat actors continued their discovery and beacon-spreading activities. Toward the end of the day, they proceeded to install AnyDesk on several servers, including a backup management host, possibly as an additional means of persistence or future command and control. Subsequently, the threat actors used PowerShell to display an alert message on multiple hosts, informing users of the Cobalt Strike infection. Afterward, they used Rclone to exfiltrate copies of backup files to the Mega[.]io cloud storage service. Although the threat actors staged a ransomware binary on the backup server, they did not immediately execute it. Instead, they waited for approximately two hours before executing it using a command line argument that included a list of target hosts. However, this initial execution attempt failed, prompting the threat actors to manually execute the ransomware payload in various ways across different hosts. Finally, the threat actors connected to a domain controller and dropped three scripts. One script copied the ransomware executable to all hosts, another reset every user's password in the organization, and the third executed the staged ransomware payload using PsExec. Upon execution, the ransomware left a ransom note named README_TO_DECRYPT.html, attributing the intrusion to Quantum ransomware. The time elapsed from the initial IcedID infection to the ransomware attack was slightly over 78 hours, during which all domain-joined systems were encrypted with Quantum ransomware. Execution The intrusion began with the execution of the IcedID malware, which was delivered within an ISO image. This ISO file was distributed to the victim as part of a malspam campaign. The use of ISO images for payload delivery is a common evasion technique employed by threat actors to bypass Mark-of-the-Web controls. When the victim clicked on the ISO file, it created a hidden directory containing the IcedID payload and a batch file. An LNK file named "documents" was visible to the user, and clicking on it triggered the batch file's execution. The batch file copied the IcedID payload to the user's AppData\Local\Temp folder and loaded it using rundll32.exe. Concurrently, a scheduled task was created to maintain persistence on the compromised host. Discovery Upon execution of the IcedID payload, the threat actors initiated various discovery commands using Windows utilities such as net, nltest, and ipconfig. These commands aimed to gather information about domain trusts, domain administrators, workstation configurations, and other network details. Approximately 16 hours after the initial execution, the first Cobalt Strike beacon DLL was executed from the IcedID malware, leading to another round of discovery using net and AdFind. Persistence The threat actors established persistence by creating a scheduled task that utilized a DLL named Utucka.dll. This scheduled task ran every hour and loaded the DLL using rundll32.exe. Privilege Escalation To escalate privileges, the threat actors employed multiple techniques, including named pipe impersonation, WinLogon token impersonation/theft, and an attempt to exploit the CVE-2020-1472 vulnerability (ZeroLogon). While some privilege escalation attempts were blocked by antivirus software, others were successful. Defense Evasion The threat actors employed several defense evasion tactics, including bypassing Mark-of-the-Web controls, tampering with Windows Defender, and using process injection techniques. They also attempted to clear the way for their activities by running a command to uninstall Windows Defender GUI. Credential Access The threat actors used various tools and scripts to access and collect credentials from compromised hosts. This included the use of Mimikatz in binary and PowerShell forms, as well as DCSync to dump credentials. Several attempts were made to access and dump LSASS memory for credential harvesting. Lateral Movement After obtaining clear-text credentials for a domain administrator account, the threat actors began moving laterally within the network. They used WMIC to conduct discovery and executed remote commands to distribute and execute Cobalt Strike beacons on other systems. Impact The attack culminated in the deployment of Quantum ransomware across all domain-connected systems. This resulted in the encryption of critical data and systems, causing significant disruption and potential data loss. Other tools In the course of the intrusion, the threat actors employed a range of additional tools and scripts, further escalating the complexity and impact of their actions. Some of the noteworthy tools and activities are detailed below: ns.bat Script Among the various binaries and scripts introduced to one endpoint, the 'ns.bat' file stands out. This script executed thousands of 'nslookup' commands, each targeting a specific hostname from the network. The outputs of these commands were aggregated into an 'ns.txt' file. ADGet - Active Directory Enumeration Tool The threat actors deployed an uncommon but effective Active Directory collection tool named ADGet. This tool was placed in a user's temporary folder and executed with an output filename parameter. ADGet was user-friendly, invoked through the command line, and allowed for specifying an output file to save enumerated Active Directory objects. ADGet differed from the more commonly known ADfind tool in that it did not rely on LDAP queries passed as parameters; instead, the queries were coded directly into the binary itself. When configured with its default settings, ADGet generated a zip output file containing several TSV (tab-separated value) files. These files could be viewed using any editor or reader that supports CSV or TSV formats. ADfind Before using ADGet, the threat actors leveraged the well-established ADfind tool. They renamed it to 'find.exe' and executed it using a batch file named 'find.bat' dropped into the ProgramData folder on one host. The 'find.bat' file contained a series of commands to query Active Directory objects, such as users, computers, organizational units, subnets, groups, and trust relationships. AD.bat: for /f "delims=" %%A in ('dir /s /b %WINDIR%\system32\*htable.xsl') do set "var=%%A" adfind.exe -f (objectcategory=person) > ad_users.txt adfind.exe -f objectcategory=computer > ad_computers.txt adfind.exe -f objectcategory=computer -csv name operatingSystem > ad_computers_enum.txt adfind.exe -f (objectcategory=organizationalUnit) > ad_ous.txt adfind.exe -subnets -f (objectCategory=subnet) > ad_subnets.txt adfind.exe -f "(objectcategory=group)" > ad_group.txt adfind.exe -gcb -sc trustdmp > ad_trustdmp.txt Notably, the first line of the batch file specified the WMI output configuration in HTML form, although this HTML was never utilized during the intrusion. It is possible that this code was borrowed or repurposed from other open-source penetration testing scripts. WMIC (Windows Management Instrumentation Command-Line) The threat actors utilized the 'WMIC' command through a batch file named 'dS.bat.' This batch file queried multiple target hosts to determine their disk drive configurations, including any mounted network shares. The 'dS.bat' file was executed through the injected 'Rundll32.exe' process. WmiPrvSe.exe (WMI Provider Host) executed the PowerShell Cobalt Strike beacon on the remote computers. Microsoft Management Console for Viewing Group Policy During the intrusion, the threat actors accessed the Group Policy using the Microsoft Management Console application. This action allowed them to review Domain Group Policy Objects, potentially yielding valuable information regarding host configurations and restrictions within the network. Lateral Movement To move laterally within the network, the threat actors employed several methods and tools: WMI (Windows Management Instrumentation): The threat actors used 'wmic.exe' to execute PowerShell Cobalt Strike beacons on multiple workstations and servers. These payloads were hosted on 'textbin[.]net,' enabling the threat actors to establish control over remote systems. Remote Desktop Protocol (RDP): The threat actors used a variety of processes, including beacon injection and standalone processes like 'Nigu.exe' and 'lsass.exe,' to initiate RDP connections. During these sessions, they often launched Internet Explorer to download additional beacons or execute commands. Remote Services: Remote services were created to facilitate the propagation of Cobalt Strike beacons across the network. Notably, AnyDesk was employed for lateral movement between a workstation and a backup server. Data Collection The threat actors actively collected data from multiple hosts using the 'dir' command, which was executed through administrative shares (e.g., c$). The collected data was then redirected to a text file named 'listing.txt.' Additionally, various text files were created to store the output of different discovery commands and scripts on compromised hosts. Command and Control The threat actors maintained control over the compromised network using various command and control (C2) servers and tools: IcedID: This malware was configured with specific details, including a campaign ID and C2 URL. Initially, it communicated over an unencrypted port (80) before switching to TLS on port 443.
